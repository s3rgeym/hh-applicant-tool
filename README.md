## Функционал

- 🤖 Поддержка ИИ
- 📤 Рассылка откликов
- ✍️ Автоматическая генерация сопроводительных
- 🧩 Решение тестов при отклике и распознание капчи
- 💬 Автоответчик в чате с работодателем, в тч для общения с ботом рекрутером
- 📧 Дополнительная рассылка писем на Email работодателям
- 👥 Поддержка нескольких аккаунтов через профили
- 📇 Сохранение контактов работодателей и информации о вакансиях
- 🔒 Данные хранятся локально, никаких скрытых зондов и отправки данных на
  сторонние сервера, а значит ваши данные не утекут в результате взлома или не будут переданы различным мошенникам
- 📖 Открытый исходный код
- 🖥️ Может запускаться на сервере. В отличии от других реализаций не использует Headless Chromium, поэтому потребляет минимальное количество ресурсов, что критично для бюджетных серверов. Хромиум сильно грузит процессор, потребляет сотни мегабайт оперативной памяти при открытии hh и требует 1-2 гигабайт свободного места. Так что утилите хватит и VDS за пару сотен.
- 🎨 Наличие простого UI
- 🎁 И другой функционал абсолютно бесплатно!

## Установка

Утилиту можно установить из `PyPi` или скачать из репозитория. Из остальных мест ее скачивать не рекомендуется.

Установка:

```bash
# Стандартный pip (в Linux только в виртуальное окружение получится установить)
$ pip install hh-applicant-tool

# Чтобы утилита поддерживала команду ui
$ pip install 'hh-applicant-tool[ui]'

# Но лучше использовать pipx
$ pipx install hh-applicant-tool

# Последнюю версию можно установить через git
$ pipx install "git+https://github.com/s3rgeym/hh-applicant-tool"

# Для обновления до новой версии
$ pipx upgrade hh-applicant-tool
```

pipx добавляет исполняемый файл `hh-applicant-tool` в `~/.local/bin`, делая эту команду доступной. Путь до `~/.local/bin` должен быть в `$PATH` (в большинстве дистрибутивов он добавлен).

Использование виртуальных окружений в Linux/Mac:

```sh
mkdir -p ~/.venvs
python -m venv ~/.venvs/hh-applicant-tool
# Это придется делать постоянно, чтобы команда hh-applicant-tool стала доступна
.  ~/.venvs/hh-applicant-tool/bin/activate
pip install hh-applicant-tool
```

Отдельно я распишу процесс установки в **Windows** в подробностях:

- Для начала поставьте последнюю версию **Python 3** любым удобным способом.
- Запустите **PowerShell** (не `CMD.EXE`, блять, а именно поверщель) от Администратора и выполните:

  ```ps
  Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy Unrestricted
  ```

  Данная политика разрешает текущему пользователю (от которого зашли) запускать скрипты. Без нее не будут работать виртуальные окружения.

Далее можно поставить `pipx` и вернуться к инструкции вверху раздела:

- Всё так же от администратора выполните:

  ```ps
  python -m pip install --user pipx
  ```

  А затем:

  ```ps
  python -m pipx ensurepath
  ```

- Перезапускаем Terminal/Powershell и проверяем:

  ```ps
  pipx -h
  ```

С использованием вирт. окружений:

- Создайте и активируйте виртуальное окружение:

  ```ps
  PS> python -m venv hh-applicant-venv
  PS> .\hh-applicant-venv\Scripts\activate
  ```

- Поставьте все пакеты в виртуальное окружение `hh-applicant-venv`:

  ```ps
  (hh-applicant-venv) PS> pip install hh-applicant-tool
  ```

- Проверьте, работает ли оно:

  ```ps
  (hh-applicant-venv) PS> hh-applicant-tool -h
  ```

- В случае неудачи вернитесь к первому шагу.
- Для последующих запусков сначала активируйте виртуальное окружение.

## Авторизация

Авторизация по коду:

```bash
hh-applicant-tool authorize '<ваш телефон>'
```

Проверка авторизации:

```bash
$ hh-applicant-tool whoami
🆔 27405918 Кузнецов Андрей Владимирович [ 📄 1 | 👁️ +115 | ✉️ +28 ]
```

В случае успешной авторизации токены будут сохранены в `config.toml`:

```toml
[token]
access_token = "USERAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
refresh_token = "USERBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBBB"
access_expires_at = 1799999999
```

Токен доступа выдается на две недели. Он обновляется автоматически. Для его ручного обновления нужно выполнить:

```bash
hh-applicant-tool refresh-token
```

Помните, что у `refresh_token` тоже есть время жизни, поэтому может потребоваться полная авторизация.

## Описание команд

Примеры команд:

```bash
# Общий вид: сначала глобальные настройки, затем команда и её аргументы
$ hh-applicant-tool [options] <operation> [args]

# Справка по глобальным флагам и список операций
$ hh-applicant-tool -h

# Справка по операции
$ hh-applicant-tool authorize -h

# Авторизуемся
$ hh-applicant-tool authorize

# Авторизация с использованием другого профиля
$ hh-applicant-tool --profile profile123 authorize

# Рассылаем заявки
$ hh-applicant-tool apply-vacancies

# Для тестирования поисковой строки и других параметров, используйте --dry-run.
# С ним отклики не отправляются, а лишь выводятся сообщения
$ hh-applicant-tool -vv apply-vacancies --search "Python программист" --per-page 3 --total-pages 1 --dry-run

# Фильтруем вакансии по исключаемым словам (fullstack, junior, php и т.п.)
$ hh-applicant-tool apply-vacancies --search "Python backend" --excluded-filter "fullstack,junior,php,java" --dry-run

# Поднимаем резюме
$ hh-applicant-tool update-resumes

# Ответить работодателям
$ hh-applicant-tool reply-employers

# Просмотр лога в реальном времени
$ hh-applicant-tool log -f

# Посмотреть содержимое конфига
$ hh-applicant-tool config

# Редактировать конфиг в стандартном редакторе
$ hh-applicant-tool config -e

# Вывести значение из конфига
$ hh-applicant-tool config -k token.access_token

# Установить значение в конфиге, например, socks-прокси
$ hh-applicant-tool config -s proxy_url socks5h://localhost:1080

# Удалить значение из конфига
$ hh-applicant-tool config -u proxy_url

# Утилита все данные об откликах хранит в SQLite
$ hh-applicant-tool query 'select count(*) from vacancy_contacts;'

# Экспорт контактов в csv
$ hh-applicant-tool query 'select * from vacancy_contacts' --csv -o
contacts.csv

# Выполнение запросов в интерактивном режиме
$ hh-applicant-tool query

# Чистим отказы
$ hh-applicant-tool clear-negotiations

# При обновлении может сломаться схема БД, для ее починки нужно выполнить
# поочерёдно все миграции, добавленные после выхода последней версии
$ hh-applicant-tool migrate
List of migrations:

  [1]: 2026-01-07

Choose migration [1] (Keep empty to exit): 1
✅ Success!

# Вывести все настройки
$ hh-applicant-tool settings

# Получить значение по ключу
$ hh-applicant-tool settings auth.username

# Установить email, используемый для автологина
$ hh-applicant-tool settings auth.username 'user@example.com'
```

Глобальные настройки:

- `-v` используется для вывода отладочной информации. Два таких флага, например, выводят запросы к **API**.
- `-c <path>` путь до каталога, где хранятся конфигурации.
- `--profile <profile-id>` можно указать профиль, данные которого будут храниться в подкаталоге.
- `--use-kitty`/`--use-sixel` использовать опр протокол для отображения капчи
  в терминале. Если не указывать, то капча будет отображена через `tkinter`, если тот установлен....
- `--use-ai`/`--ai` использовать автоматизацию распознания капч и прочих
  действий через ИИ.

> [!IMPORTANT]
> Почитайте про [язык для поисковых запросов](https://hh.ru/article/1175). Он позволяет отсеивать мусор при поиске подходящих вакансий, например, `(Go OR Golang) NOT PHP NOT JavaScript`.

Утилита использует систему плагинов. Все они лежат в [operations](https://github.com/s3rgeym/hh-applicant-tool/tree/main/src/hh_applicant_tool/operations). Модули, расположенные там, автоматически добавляются как доступные команды. За основу для своего плагина можно взять [whoami.py](https://github.com/s3rgeym/hh-applicant-tool/tree/main/src/hh_applicant_tool/operations/whoami.py).

Для тестирования запросов к API используйте команду `call-api` совместно с `jq` для обработки JSON.

Пример поиска работодателей:

```bash
$ hh-applicant-tool call-api /employers text="IT" only_with_vacancies=true | jq -r '.items[].alternate_url'
https://hh.ru/employer/1966364
https://hh.ru/employer/4679771
...
```

Синтаксис `call-api` немного похож на `httpie` или `curlie`:

```sh
hh-applicant-tool call-api [{GET|POST|PUT|DELETE}] <endpoint> [<key=value> ...]
```

Если используется метод `GET` или `DELETE` (или ничего не указано), то параметры будут переданы как query string. Во всех остальных случаях параметры передаются как `application/x-www-form-urlencoded` в теле запроса.

Для поиска вакансий по региону в `apply-vacancies` нужно указать параметр `area`. Можно его указывать как для страны (каз - 40, бел - 2238), так и отдельного города (мск - 1).

Пример поиска `area id` по стране и названию:

```sh
$ hh-applicant-tool api /areas | jq -r '.[] | select(.name == "Беларусь") | .. | objects | select(.name == "Барановичи")'
{
  "id": "2239",
  "parent_id": "2233",
  "name": "Барановичи",
  "areas": [],
```

## Капча

Если вызов какого-то метода API генерирует ошибку капчи, то она перехватывается, а далее происходит следующее:

- при флаге `--use-ai` капча будет распознаваться нейронкой
- иначе:
  - капча отображается в терминале, если есть флаги `--use-kitty`/`--use-sixel` с именами используемых протоколов для отображения изображений (первый поддерживает даже Windows Terminal)
  - в противном случае капча будет отображена через всплывающее окно `tkinter`

Некоторые модели плохо распознают русский язык, английский для можно установить с помощью передачи `--captcha-lang EN`.

## Запуск через Docker

Это рекомендованный разработчиком способ. Если не работает стандартная установка, то используйте его. Также это самый простой способ запуска и использования утилиты, требующий скопипастить 5 команд.

Для начала нужно установить `docker` и `docker-compose`:

```sh
sudo apt install docker.io docker-compose-v2
```

Выкачиваем репозиторий и переходим в каталог:

```sh
git clone https://github.com/s3rgeym/hh-applicant-tool
cd hh-applicant-tool
```

> [!IMPORTANT]
> Команды с docker-compose нужно запускать строго, находясь в данном каталоге!

Теперь авторизуемся:

```sh
# Чтобы ввести капчу в терминале укажите флаги --use-sixel/-s или --use-kitty/-k
# Это названия протоколов, которые исп-ся терминалом для отображения изображений
# Sixel поддерживается большинством терминалов
# А вот Windows Terminal поддерживает только Kitty
docker-compose run -u docker -it hh_applicant_tool \
  hh-applicant-tool -s -vv auth <username>
```

Если использовать флаг `--ai`, то капча будет разгадана нейронкой и останется только ввести код подтверждения из SMS/Email.

Подробно про авторизацию можно почитать [здесь](#авторизация).

В случае успешной авторизации можно запускать рассылку откликов по крону:

```sh
docker-compose up -d
```

Что будет делать?

- Рассылать отклики со всех опубликованных резюме.
- Поднимать резюме.

Просмотр логов `cron`:

```sh
docker compose logs -f
```

Чтобы прекратить просмотр логов, нажмите `Ctrl-C`.

Информацию об ошибках можно посмотреть в файле `config/log.txt`, а контакты работодателей — в `config/data` с помощью `sqlite3`. В `config/config.toml` хранятся токены, дающие доступ к аккаунту.

Также советую отредактировать файл `letter.txt`.

Запущенные сервисы докер стартуют автоматически после перезагрузки. Остановить их можно выполнив:

```sh
docker-compose down
```

Чтобы обновить утилиту, в большинстве случаев достаточно в каталоге выполнить:

```sh
git pull
```

В редких случаях нужно пересобрать все:

```sh
docker compose up -d --build
```

Чтобы рассылать отклики с нескольких аккаунтов, нужно переписать `docker-compose.yml`:

```yaml
services:
  # Не меняем ничего тут
  hh_applicant_tool:
    # ...

  # Добавляем новые строки

  # Просто копипастим, меняя имя сервиса, container_name и значение HH_PROFILE_ID
  hh_second:
    extends: hh_applicant_tool
    container_name: hh_second
    environment:
      - HH_PROFILE_ID=second

  hh_third:
    extends: hh_applicant_tool
    container_name: hh_third
    environment:
      - HH_PROFILE_ID=third

  # Общий шаблон для новых профилей
  уникальное_имя_сервиса:
    extends: hh_applicant_tool
    # может совпадать с именем сервиса
    container_name: уникальное_имя_контейнера
    environment:
      - HH_PROFILE_ID=название_профиля
```

> [!IMPORTANT]
> В этом файле важны отступы!

Обратите внимание на `HH_PROFILE_ID` — его значение указывается при авторизации, если профиль отличен от дефолтного. Далее нужно авторизоваться в каждом профиле:

```sh
# Авторизуемся со второго профиля
docker-compose exec -u docker -it hh_applicant_tool \
  hh-applicant-tool --profile-id second -k auth

# Авторизуемся с третьего профиля
docker-compose exec -u docker -it hh_applicant_tool \
  hh-applicant-tool --profile-id third -k auth

# И так далее
```

Ну и выполнить `docker-compose up -d`, чтобы запустить новые сервисы.

[Команды](#описание-команд) можно потестировать в запущенном контейнере:

```sh
$ docker-compose exec -u docker -it hh_applicant_tool bash
docker@1897bdd7c80b:/app$ hh-applicant-tool config -p
/app/config/config.toml
docker@1897bdd7c80b:/app$ hh-applicant-tool refresh-token
ℹ️ Токен не истек, обновление не требуется.
docker@1897bdd7c80b:/app$
```

> [!IMPORTANT]
> Обратите внимание, что `docker-compose exec`/`docker-compose run` запускаются с аргументами `-u docker`. Только для пользователя `docker` установлен `chromium`, необходимый для авторизации, а также это избавляет от проблем с правами, когда созданные файлы для изменения требуют root-права.

Если хотите команду `apply-vacancies` вызывать с какими-то аргументами, то создайте в корне файл `apply-vacancies.sh`:

```sh
#!/bin/bash

# Пример с фильтрацией по исключаемым словам
/usr/local/bin/python -m hh_applicant_tool apply-vacancies \
  -l letter.txt \
  --excluded-filter "fullstack|junior|php" # укажите любые аргументы
```

В файлах `startup.sh` и `crontab` замените `/usr/local/bin/python -m hh_applicant_tool apply-vacancies` на `/bin/sh /app/apply-vacancies.sh`.

### Конфигурационный файл

> В TOML разрешены multiline strings (в русском line и string переводятся

> хранения различных шаблонов

Главный конфиг называется `config.toml`. Он содержит основные настройки. Полный путь до конфигурационного файла можно вывести с помощью команды:

```bash
hh-applicant-tool config -p
```

```toml
# Прокси для запросов к hh.ru
# Приоритет: флаг --proxy-url, затем этот параметр, затем переменные окружения HTTP_PROXY / HTTPS_PROXY

connect_timeout = 10.0               # таймаут соединения, сек, по умолчанию 10
max_retries = 3                      # число повторов при сетевых ошибках и лимитах, по умолчанию 3
```

## Шаблоны сообщений

- **`%(vacancy_name)s`**: Название вакансии.
- **`%(vacancy_url)s`**: Ссылка на вакансию.
- **`%(employer_name)s`**: Название работодателя.
- **`%(first_name)s`**: Имя пользователя.
- **`%(last_name)s`**: Фамилия пользователя.
- **`%(email)s`**: Email пользователя.
- **`%(phone)s`**: Телефон пользователя.
- **`%(resume_title)s`**: Название резюме.
- **`%(resume_hash)s`**: Идентификатор резюме.
- **`%(resume_url)s`**: Ссылка на резюме.

Эти плейсхолдеры могут быть использованы в сообщениях для отклика на вакансии. Например:

```
Меня заинтересовала ваша вакансия %(vacancy_name)s. Прошу рассмотреть мою кандидатуру. С уважением, %(first_name)s %(last_name)s.
```

Также можно делать текст уникальным с помощью `{}`. Внутри них через `|` перечисляются варианты, один из которых будет случайно выбран:

```
Увольте того {идиота|придурка}, который придумал этот {тупой|сраный|дурацкий} вопрос.
```

В итоге получится что-то вроде:

```
Увольте того идиота, который придумал этот сраный вопрос.
```

`{}` могут быть вложенными.

| `HTTPS_PROXY` / `https_proxy` | Прокси для HTTPS-запросов к API HH; если не задан — используется HTTP-прокси                                                           |

## Интеграция и использование в скриптах

Если хотите использовать `hh-applicant-tool` в своих скриптах, то можно это сделать так:

```python
from hh_applicant_tool import HHApplicantTool

tool = HHApplicantTool()
print(tool.api_client.get('/me'))

# Какую-то вспомогательную информацию можно сохранять в настройках
import datetime as dt

tool.storage.settings.set_value("_last_script_run", dt.datetime.now())

# Учтите, что в таком случае токены, которые могут обновиться при выполнении запросов,
# нужно сохранять вручную
tool.save_token()
```

Команды тоже можно вызывать:

```python
>>> from hh_applicant_tool import HHApplicantTool
>>> HHApplicantTool().run(["auth", "v.pupkin@mail.ru"])
```

Если же утилита интегрируется в графические приложения, то как правило должна быть возможность отменить текущую операцию:

```python
import multiprocessing as mp

from hh_applicant_tool import HHApplicantTool

def run_command(argv: list[str]):
    HHApplicantTool().run(argv)

p = mp.Process(target=run_command, args=(['apply-vacancies', ...],))
p.start()

# Убили процесс
p.terminate()

# Ждем пока не помрет
p.join()
```

## Принцип работы

> [!IMPORTANT]
> Данной утилите похуй на "запрет" доступа к API HH сторонним приложениям, так как она прикидывается официальным приложением под Android

Долгое время я делал массовые заявки с помощью консоли браузера:

```js
$$('[data-qa="vacancy-serp__vacancy_response"]').forEach((el) => el.click())
```

Оно работало, хоть и не идеально: например, при отклике на некоторые вакансии перебрасывало на другую страницу. Поэтому я пробовал автоматизировать рассылки через `p[yu]ppeteer`, пока не прочитал [документацию](https://github.com/hhru/api) и не обнаружил, что **API** (интерфейс) содержит все необходимые мне методы. Headhunter позволял создавать свое приложение, но там была ручная модерация, а палиться в нарушении правил пользования сайтом (автоматические отклики запрещены) не хотелось. И тогда я [декомпилировал](https://gist.github.com/s3rgeym/eee96bbf91b04f7eb46b7449f8884a00) официальное приложение для **Android**, получил **CLIENT_ID** и **CLIENT_SECRET**, необходимые для работы через **API**.

Позже оказалось, что работы только через **API** недостаточно. Например, в нем нет методов для решения тех же тестов. Поэтому для их решения приходится эмулировать работу через сайт. Точно так же обстоят дела с решением капчи. **API** буквально нам предлагает открыть страницу с капчей в браузере, решить ее, а потом вызвать нужный метод **API** снова.

Сам сайт ХХ использует React. На каждой странице есть тег `<template id="HH-Lux-InitialState"></template>`. Внутри него заключен JSON `{"redirectConfig":....}`, в котором разделители заменены на HTML-сущности. В нем содержатся данные, необходимые для рендеринга страницы. Если нужно спарсить какие-то данные с веб-версии (у них она называется десктопной), то искать их стоит там. Там, кстати, много лишнего хранится: от ссылки на бота в Telegram для сотрудников поддержки сайт до страниц каких-то инфоцыган (этот уебанский сайт ставку сделал на зарабатывание денег на соискателях, я это осуждаю в отличии от доения тамошних работодятлов с их тупорылыми херками).

Сами эндпоинты сайта работают довольно странно. Параметры могут передавать через тело, Query String, через куки и заголовки. Но не всегда, на отдельных эндпоинтах обязательна передача в теле запроса.

Так же при авторизации на сайте вам выдается `xsrf` токен, он используется во всех запросах, отправляемых через `XMLHttpRequest`...

Для решения капчи нужен `captchaState`. Его возвращают некоторые эндпоинты сайта к которым обращаются через `XMLHttpRequest`. Либо он содержится в ссылке. Далее нужно получить `captchaKey`, послав POST-запрос без тела на эндпоинт сайта `/captcha?lang=RU` (можно указать еще `EN`). После получения `captchaKey` мы грузим изображение `/captcha/picture?key=<captchaKey>`. Ну и далее решение капчи, `captchaState` и `captchaKey` отправляются на POST-запросом на `/account/captcha`. Этот процесс тут описан упрощенно. Там еще нужно отправлять специальные заголовки... А так сама по себе капча существует словно отдельно от сайта... Ну у них там и микрофронтенды используются... Там говнокодеры ебучие работают.

Самым сложным был "взлом" процесса авторизации. Мне пришлось два часа лазать искать как `loginTrustFlags` генерируются для "подписи" данных отправляемых при авторизации. Для этого мне пришлось во вкладке отладчика браузера `Sources` отрелактировать скрипты на сайте, вставив в нужные места `console.log`/`console.dir`/`console.table` перед `debugger;` (для этого нужно выбрать директорию для синхронизации, тогда станет доступна возможность редактировать скрипты "прямо на сайте"). Там на странице входа из объекта с `redirectConfig` берется `loginTrustFlagsSecret`. В нем содержится публичный сертификат, которым шифруется такой JSON:

```js
{"emailOrPhone":{"paste":false,"suggest":true},"ts":Date.now()}
```

По названиям полей несложно догадаться, что там указывается был ли логин вставлен в поле или выбран из выпадающего списка при вводе. Боты, которые работают через Headless Chromium обычно ничего не вставляют и не выбирают из выпадающего списка, а "печатают"...

> При авторизацию по паролю такое шифруется: {"password":{"suggest": false,"paste": false},"ts":...}

Далее этот объект пропускается через `JSON.stringify` и шифруется с помощью публичного ключа. Используется ассимитричное шифрование `RSA-OAEP` с хешированием `SHA-256` и кодированием в base64. Без этой подписи запроса авторизоваться не получится.

Без расстановки контрольных меток быстро данную функцию шифрования можно найти так: жмем `Ctrl-Shift-F` во вкладке `Sources` и вводим `await crypto[`, ниже будет что-то типа:

```js
// С каждой версией фронтенда имена переменных меняются
const _0x3cd982 = {
  ..._0x334204,
  // 'ts': Date['now']()
  '\x74\x73': Date[_0x50c3ac(0x13f, '\x51\x47\x76\x23')](),
};

// Добавляем и смотрим что шифруется в trustLoginFlags...
console.log('trust login: %o', _0x3cd982);
```

Большинство эндопоинтов шифрует лишь JSON с таймстермп наподобии такого: `{"ts":1791234567890}`. Я думаю, что кроме `ts` там обязательных полей нет.

В принципе больше нечего рассказать...

Таким образом моя утилита работает в гибридном режиме: через API и веб-версию. При этом она не использует Headless Chromium ни для авторизации, ни для решения капчи...

## Разработка

- `git clone ...`
- `poetry install .`
- **poetry** можно установить через **pipx**
- в дальнейшем можно запускать утилиту так `poetry run hh-applicant-tool authorize`
- либо можно активировать виртуальное окружение, которое создается в каталоге проекта (`source .venv/bin/activate`)
- после изменений ничего переустанавливать не надо (`poetry install` устанавливает проект в режиме редактирования, те все изменения в каталоге проекта "сразу применяются")

Для публикации новой версиии утилиты на `PyPi` нужно указывать версию. Она указывается в `pyproject.toml`. Когда делаете `Pull Request`, то увеличивайте эту версию на единичку (при малозначительных изменениях — последнее число).
